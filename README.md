# LabBridge

**面向二甲及乡镇卫生院的检验数据桥接 Demo。**把仪器数据与纸质报告汇入统一记录，全程脱敏、留痕、可追溯。

| 项 | 值 |
|---|---|
| 运行时依赖 | **零第三方** —— 纯 Python 标准库，无需 `pip install` |
| 代码规模 | 主程序 3231 行 + 15 个核心模块 7117 行 |
| 界面 | tkinter GUI，11 个功能页签 |
| 运行环境 | Python 3（构建与验证环境为 3.14，需自带 tkinter） |
| 许可 | MIT |

---

## 一、它解决什么问题

基层检验科有三个绕不开的现实：**仪器有数据但取不出来**、**老设备没接口只能手抄**、**数据必须留在院内但又必须能溯源审计**。

LabBridge 用两条轨道覆盖前两个问题，用一套本地审计机制回答第三个：

- **轨道 A（直连）**：实现 ASTM E1381 / E1394 只读接收端，直接接管仪器吐出的数据流。
- **轨道 B（兜底）**：对没有数据接口的老设备，走拍照 OCR 抽取 + 人工确认，不改造设备即可录入。

两条轨道汇入同一套脱敏、审核、留痕管线，最终产出可归档、可审计的检验记录与证据包。


## 三、核心设计取舍

**1. 审计日志用哈希链，而不是"记个文件"**
每条日志带 `prev_hash`，改任意一条、或删中间任意一段，校验都会立刻断链。这是"可追溯"能站得住的技术前提，而不是靠流程承诺。

**2. 红线门禁在代码里，不在文档里**
5 条红线（数据不出院、禁止明文留存 PII、无审批不处置等）以 `labbridge_gate.py` 中的 `REDLINES` 常量形式强制执行，违反即拦截，而非依赖使用者自觉。

**3. 零第三方运行时依赖**
不是偷懒，是主动选择：基层环境常常没有稳定的外网与运维能力，零依赖意味着无供应链风险、无许可费用、无版本冲突。代价是 YAML 解析、MCP 协议、SAS XPORT 解析等能力都需自行实现（见 `labbridge_config.py`、`labbridge_mcp.py`、`labbridge_nhanes.py`）。

**4. 第三方组件的许可合规经过逐一审查**
社区里能用的轮子很多，但授权条款未必允许商用。`docs/09_GitHub社区Agent与Skill选型清单.md` 逐项标注了"可直接用 / 可重写 / 重写也没用"的判定与依据，`THIRD_PARTY_NOTICES.md` 记录了最终结论。

## 四、模块结构

主程序 `labbridge_v2_app.py` 负责 GUI，`code/` 下 15 个模块为可独立复用的业务核心（**不依赖 tkinter，也不依赖任何 Windows API**，可直接移植到服务端）：

| 模块 | 职责 |
|---|---|
| `labbridge_astm.py` | 轨道 A：ASTM E1381 / E1394 只读接收端 |
| `labbridge_ocr.py` | 轨道 B：拍照 OCR 抽取与人工确认 |
| `labbridge_deid.py` | 脱敏与访问控制引擎 |
| `labbridge_screen.py` | 审核规则引擎与熔断检测 |
| `labbridge_auditlog.py` | 审计日志中间件（哈希链防篡改） |
| `labbridge_evidence.py` | 证据包 / 资产包 / 验收断言 / CAPA |
| `labbridge_gate.py` | 红线自检 · 阶段门 · 审批门 |
| `labbridge_pdca.py` | PDCA 质量工具集（SPC、FMEA、控制图等 36 项） |
| `labbridge_config.py` | 配置层（含 YAML 子集解析器） |
| `labbridge_report.py` | 证据报告生成器（docx） |
| `labbridge_docparse.py` | 文档解析管线 |
| `labbridge_mcp.py` | MCP Server（零依赖实现） |
| `labbridge_nhanes.py` | NHANES 真实公开数据回放 |
| `labbridge_apibridge.py` | 外部接口对接桥（ASTM / OCR / LIS / LLM） |
| `labbridge_demo.py` | 端到端 Demo 编排器 |
