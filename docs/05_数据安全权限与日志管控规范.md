# 05 · 数据安全 · 权限 · 日志管控规范

> 项目代号：LabBridge（面向二甲及乡镇卫生院的检验数据桥接）
> 文档集版本：V4.2 ｜ 编制日期：2026-10-30
> 对应软件版本：V2.5.2 ｜ 对应封包：`LabBridgeV4`
> 适配标准：ISO 9001:2026、ISO/IEC 42001:2023，部分参考 ISO 13485:2016
> 本文职责：定义数据分级、四级权限矩阵、双轨日志 Schema 与人在回路审计规则（对应 ISO 9001 7.5、ISO/IEC 42001 数据治理与人在回路要求）

## 一、管控总原则：人定规则、机器执行、人审例外

| 层级 | 谁来做 | 产出 | 说明 |
|---|---|---|---|
| **规则层** | 人（一次性定义） | 人签署的《分类分级规则文件》 | 例如「字段名含身份证/手机号/薪酬 → L3 以上敏感」。**这是审计员真正会检查的受控信息** |
| **执行层** | 机器（自动打标） | 分类分级推荐结果 | 结合 DDL 元数据与字段描述自动推荐；人对每条结果选择「应用」或「弃用」，注意力集中在置信度低或后果高的例外项 |
| **例外层** | 人（只处理少数） | 例外审批记录 | 只处理机器不确定或规则未覆盖的情况 |

**关键转变**：人的角色从「逐条审批者」变成「规则制定者 + 例外裁定者」，数据量再大也不会线性放大人的工作量。

> 「人定规则、机器执行、人审例外」应写进 Demo 的系统提示，它是回答「为什么 AI 可以碰数据」的标准答案。

## 二、数据分级体系

### 2.1 三级数据分类（与 02 号文档一致）

| 数据类别 | 定义 | 典型内容 |
|---|---|---|
| 公共数据 | 可对外公开，无企业业务信息 | ISO 标准原文、公开行业指南、公开培训案例、ASTM E1381/E1394 公开协议规范 |
| 非敏感数据 | 企业内部可共享，不含机密隐私 | 空白表单、通用内审记录模板、脱敏后的结构化检验字段 |
| 敏感数据 | 企业/机构核心机密，受质量、数据合规约束 | IVD 质控数据、患者身份信息（姓名、出生日期、地址、电话）、原始检验报告与单据图像、工艺参数、内部不合格报告 |

### 2.2 分级粒度：字段级 + 行级，不是表级

放弃「表级分级」，转向**字段级和行级的动态授权**：

- 大表在元数据层面拆解为**字段**，每个字段有自己的敏感等级；
- **行**的可见范围由与请求者身份绑定的属性决定；
- 采用**映射表**方案：一张查阅表——每个用户一行，每个访问维度（区域、部门、PII 权限级别）一列，行过滤和列掩码由这张表统一驱动；
- 字段呈现**原文 / 掩码 / 隐藏**，由请求者权限级别 + 该行数据的业务属性共同判定。

**评审对象**：字段清单和映射规则，而不是表里的每一行数据。规则一旦确定，每次查询的授权判断由策略引擎在运行时完成。

### 2.3 三级梯度上线顺序

公开测试数据 → 脱敏数据 → 受控敏感数据。

每一级上线前须完成对应管控措施的部署与评审，**未通过不得进入下一级**。

| 系统配置/密钥/日志 | 原文 | 隐藏 | 隐藏 | 隐藏 |

> 敏感·患者身份信息例外查看规则（V2 优化项第 10 条，已落地于 GUI「敏感信息查看」页）：工程师须主任级别密码确认；主任须另一主任级别密码确认；**若主任仅一人，可直接密码确认，但 SOP 输出风险项说明、软件不提示**。
> 上表为 Demo 默认配置，正式项目按场景校准；每一次例外放行须留审批记录（见第六节）。

### 3.3 权限设置说明

- 权限默认**最小授予**，例外需显式申请与审批；
- 工程师的全域权限**同样受日志约束**——权限大不等于不可追溯；
- 角色变更、权限变更须走变更控制程序并记录。

### 3.4 职责分离（V2.5 落地）

检验与审核必须由不同人执行，否则"审核"只剩签字形式：

- 每条记录落库时写 `created_by / created_role / created_at`，凭证上可判定"谁录的"；
- 审核动作校验 `created_by ≠ 当前用户`，同一人审核自己的记录被拒；
- 一人科室确实无法分离时，**主任可破例自审**，但须填写理由，写入 `record_selfapprove` 审计事件；
- 证据包《人工审核记录》增「录入人 / 是否本人审核」两列，外审可直接看分离情况。

> **口令边界（诚实标注）**：DEMO 口令为公开值（1111/2222/3333/4444）。落盘做了本地混淆
> （`enc:v1:`，随机盐 XOR + Base64），**不是哈希**——能挡"记事本打开就看到"，挡不住能同时
> 读到 `users.json` 与 `.apikey.salt` 的本机攻击者。同一口令既能通过审批、又能重签配置，
> 因此签署主体在证据上尚不成立；要使它成立需口令哈希 + 操作员唯一身份，属上线前待办。

## 四、准入资质前置筛选

医共体跨院数据交互平台的硬性合规门槛：

- 等保 2.0 三级；
- 商用密码应用安全性评估（密评）；
- 医疗健康数据安全专项评估。

**缺任一资质将直接关停跨院数据互通权限。**

Demo 阶段虽不涉及跨院大规模互通，但若计划通过医共体打包进入，供应商本身或其所依托的云底座必须具备这三项合规能力。**优先选择已内置等保三级策略、国密加密传输和审计脱敏能力的底座，而不是事后补合规。**

## 五、架构层面的「最小暴露面」

1. **原始数据不集中上云**：二甲侧 ASTM 抓取结果在本地/边缘完成标准化和脱敏后再决定是否上云；乡镇侧原始图像留在手机或本地，云端只接收脱敏结构化字段。
2. **脱敏默认开启**：ASTM 接收端默认 redact 患者身份字段，日志和存储中不应出现可识别个人身份的信息。
3. **审计日志完整**：每一次数据接收、脱敏、AI 标记、输出都要有可追溯记录——这是 Demo 向医院证明「出了事能定位」的核心卖点。

## 六、日志规范

### 6.1 必须生成日志的四类场景

| # | 场景 | 要求 |
|---|---|---|
| 1 | **重要活动** | 必须生成日志 |
| 2 | **开发期间的变动** | 所有变动及变动区域必须生成日志 |
| 3 | **运行中的重要错误** | 必须生成日志 |
| 4 | **有人参与的动作** | 必须生成日志 |

### 6.2 有人参与的动作必须显式输出

有人参与的**审核、撤回、确认**等动作必须输出，且**具体到账户 ID 或操作人员名字**。不接受「系统已审核」「已确认」这类无主体的记录——审计追溯的第一诉求就是「谁干的」。

### 6.3 日志字段 Schema（16 字段，顺序即落盘顺序，见 `labbridge_auditlog.py` FIELDS）

> **落地范围说明（V3.1 修订，V4 沿用）**：16 字段 Schema 适用于**模块链路**产出的日志——
> `api_audit.jsonl`（脱敏/审核规则/熔断处置审计）、`nhanes_audit_log.jsonl`、
> PDCA 等命令行工具日志。GUI 界面自身的双轨日志（`data_log.jsonl` / `op_log.jsonl`）
> 为 **9 字段精简视图**（`seq/event_id/ts/action/actor/role/detail/prev_hash/hash`），
> 原因是界面动作只记"谁在何时做了什么"，对象与分级信息放在 `detail` 内。
> 两者都使用同一套哈希链算法（`sha256(去掉 hash 字段的规范化内容)` + `prev_hash` 前向指针），
> 校验规则一致。**对外举证优先使用处置审计与证据包**，界面日志作为操作轨迹补充。

| 字段 | 说明 |
|---|---|
| `event_id` | 事件唯一标识 |
| `seq` | 自增序号（哈希链用） |
| `timestamp` | 时间戳（见第七节） |
| `actor_id` | 账户 ID / 操作人员姓名（人工动作必填） |
| `actor_role` | 工程师 / 主任 / 组长 / 检验员 / system |
| `action` | 接收 / 脱敏 / 检索 / 标记 / 输出 / 审核 / 撤回 / 确认 / 变更 |
| `object` | 作用对象（表名.字段名、记录 ID、标本号） |
| `data_class` | public / internal / sensitive |
| `field_form` | 原文 / 掩码 / 隐藏 |
| `policy_hit` | 命中的策略规则 ID（如 PII-L3-mask） |
| `agent_version` | Agent 与模型版本 |
| `data_source` | 数据来源（ASTM 轨道 A / OCR 轨道 B / 知识库） |
| `human_involved` | 是否触发人工介入 |
| `result` | 成功 / 失败 / 拒绝 / 超时 |
| `prev_hash` | 上一条记录哈希（哈希链前向指针） |
| `hash` | 记录内容哈希：`sha256(规范化内容 + prev_hash)` |

任何删除、插队、篡改都会导致 `verify_chain()` 校验失败。

### 6.4 三路日志落地事实（V4）

| 日志 | 路径 | 内容 | 可见性 | 导出 | 审计地位 |
|---|---|---|---|---|---|
| 数据结果日志 | `v2_data/data_log.jsonl` | 数据结果具体内容 | 对外可查 | CSV（UTF-8 BOM） | 可作 9001 审计证据 |
| 人员操作日志 | `v2_data/op_log.jsonl` | 人员操作行为 | 仅工程师可见 | CSV（UTF-8 BOM） | **不作 9001 审计证据**，仅保留痕迹 |
| 处置审计 | `v2_data/api_audit.jsonl` | 脱敏字段处置、规则命中、熔断判定 | 对外可查 | CSV（UTF-8 BOM，16 字段） | **核心处置证据**，随证据包导出 |

日志溯源支持按**哈希值 / event_id** 查询日志与记录位置；三个日志源均提供「校验哈希链」。
日志按 5 MB 分段轮转（`data_log.jsonl.000001.jsonl` …），跨段链连续，校验时按 seq 顺序扫描全部分段。

> **V4 补充**：V3 曾发生 `restore_data` 由「解压覆盖」实现导致**归档段未被覆盖、恢复后 `prev_hash` 断链且条数翻倍**的缺陷（V3.3 / 软件 V2.5.1 修复，改为整目录替换）。该缺陷在审计上等同于「日志被篡改」。教训：**任何涉及日志目录的整体操作（备份/恢复/迁移）都必须以「原子整体」而非「逐文件合并」的方式执行**，否则哈希链语义被破坏。回归断言已纳入 `test_v240.py`（第 15 组，共 6 项）。

### 6.5 证据包构成（V2.5 定义，V4 沿用）

外审拿到的证据包必须能**独立**回答以下问题，否则包只有形式完整性、没有审计价值：

| 外审会问 | 包内依据 |
|---|---|
| 数据本身是什么 | `数据结果日志.jsonl` |
| 脱敏/规则/熔断怎么处置的 | `处置审计_api_audit.jsonl` |
| 谁审核的、是否本人审核 | `人工审核记录.md`（含录入人与审核人两列） |
| 当时生效的阈值与角色矩阵是哪版 | `受控配置_副本/critical_values.yaml`、`roles.yaml`、`SHA256SUMS` |
| 配置是否被本地重签过 | `manifest.json` 的 `config` 段（签署人/时间/原因/重签次数/被覆盖原签署人） |
| 操作序列 | `操作日志摘录_op_log.jsonl`（只出序号/时间/动作/主体/原因，不出内部绝对路径） |

`MANIFEST.sha256` 保护 `manifest.json`，`manifest.json` 逐文件（含子目录）保护上述内容，改动任一文件即失配。

> **边界**：以上证明"包没被改过"，不证明"操作本身合规"。后者依赖 `roles.yaml` 的资质对照
> 与 3.4 的分离校验共同支撑；两者缺一，证据包不足以支撑审计结论。

#### 6.5.1 交付目录零残留规则（V4 新增）

运行时数据（`v2_data/`：日志、账户 `users.json`、密钥 salt `.apikey.salt`、证据包、PDCA 运行目录）**不得随交付包分发**。理由：

1. `.apikey.salt` 与账户数据一并泄露会削弱 3.4 节的本地混淆防护；
2. 交付包内若预置日志，接收方无法判断该日志是样品还是在本地产生过；
3. PDCA 时间戳目录属于「运行结果」，混入交付物会污染「每次运行不覆盖历史」的语义。

**出包前必检**：`find <交付根> -name v2_data -o -name ".apikey.salt" -o -name "users.json"` 应无命中；本机保留过程数据，清理后才上报 FAIL。V4 已在出包时执行并命中 `app/v2_data/.apikey.salt` 一项，已清理，证据见 `03_验收审计/V4封包验收报告_2026-10-30.md`。

## 七、时间戳与哈希值确认

- 每一次数据接收、脱敏、AI 标记、输出、人工审核都锚定**时间戳**；
- 关键记录（规则文件、例外审批记录、运行时访问日志）附加**哈希值**，用于事后完整性校验；
- 三类受控文件各自在生成时锚定时间戳，内审时才能证明：**分级规则在某个时刻被批准，并在之后的每一次访问中实际执行了**。

**证据链闭环公式**：

```
规则文件（人签署 + 时间戳）
  → 例外审批记录（人裁定 + 时间戳）
    → 运行时访问日志（机器执行 + 时间戳 + 哈希）
      ⇒ 可证明「规则被批准且被真实执行」
```

## 八、人在回路审计：风险触发 + 事后抽样

人工审计不可能覆盖全部 AI 操作：**让人的注意力只流向高风险节点，低风险节点靠事后抽样和自动化规则兜底**。

### 8.1 按可逆性与影响范围分层

| 风险档 | 判定 | 处置 |
|---|---|---|
| 低风险（只读查询、可逆操作） | 后果可控、可撤销 | **自动执行 + 事后抽样审计** |
| 中风险 | 影响局部、部分可逆 | **触发人工审批** |
| 高风险（不可逆、影响临床结论） | 后果严重 | **强制人工审批，禁止全自动** |

### 8.2 审批的四个必备要素

审批时不能只弹「是否执行」，必须携带：

1. **动作计划**（要做什么）
2. **预期影响**（影响什么）
3. **风险提示**（可能出什么问题）
4. **回滚方案**（出问题怎么撤回）

> **审批超时默认拒绝**，避免无人值守时高风险操作被放行。

#### 8.2.1 受控配置重签的留痕要求（V2.5）

哈希清单只能发现"文件被改"，防不住"改完再重签"。因此重签本身必须留痕：

- 强制填写**变更原因**，写入 `SHA256SUMS` 头部；
- 记录**重签次数**与**被覆盖的原签署人**；签署人不同时界面明示"原签署人已被覆盖"；
- 重签动作写 `config_resign` 审计（含原因与被覆盖者），并随证据包以摘录形式交付。

这样"发布基线签署"与"本地操作员重签"在凭证上可区分，签署主体才具备证据意义。

### 8.3 运行时证据（外审真正看的东西）

ISO 42001 审核员关注的是**运行时证据**：策略在数据被 Agent 触碰的那一刻是否真的生效。每一笔授权判断和工具调用都需留下可关联记录——**谁、在什么上下文、基于哪条策略、读取了哪个字段的何种形态、是否触发了人工介入**，形成从输入到结果的因果链。可复核记录需关联：用户身份、Agent 与模型版本、数据来源、策略命中、人工确认。

### 8.4 两条回路的边界

| 场景 | 回路的是什么 | 不回路的是什么 |
|---|---|---|
| 数据分级 | 规则审批、例外裁定 | 逐条数据打标 |
| 审计 | 风险触发的审批、事后可验证的运行时日志 | 全量事前审批 |

两条线都不依赖人海，但都要求**规则、例外、运行时日志三样东西被受控地留存下来**。

## 九、受控配置解析等价性（V3 教训，V4 保留）

| 项 | 内容 |

## 十、合同与责任三条底线

Demo 的 POC 协议中应写入三条底线：

1. **泄露通知时限**；
2. **因桥接层过错导致的损失赔偿责任**；
3. **医院有权对桥接层的安全措施进行审计或测试**。

以 POC 附件形式体现，成本极低，但能显著降低医院的决策顾虑。

```python
def authorize(user, field, row):
    level = field.sensitivity                 # 字段级等级（规则层产出，机器执行）
    attrs = access_map[user.id]               # 用户属性行：区域/部门/PII权限级别
    if not row_filter_ok(attrs, row):
        return DENY
    form = form_matrix[attrs.pii_level][level]  # 原文 / 掩码 / 隐藏
    audit_log(actor=user.id, action="read", object=f"{field}", field_form=form,
              policy_hit=f"{level}-{form}", human_involved=False, timestamp=now(),
              hash=sha256(payload))
    if form == "原文" and level == "sensitive":
        return require_human_approval(payload_with_plan_impact_risk_rollback)
    return form
```
