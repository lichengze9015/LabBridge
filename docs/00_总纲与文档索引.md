## 一、三级版本约定（防漂移）

同一套资产有三个版本号，混用是 V3 文档的主要缺陷来源。V4 起明确分离：

| 版本对象 | 含义 | 当前值 | 变更触发条件 |
|---|---|---|---|
| 文档集版本 | 本套 00–12 立项文档的受控版本 | **V4.2** | 任一文档发生实质性内容变更 |
| 软件版本 | `labbridge_v2_app.py` 中 `APP_VERSION` 常量 | **V2.5.2** | 程序逻辑变更 |
| 封包版本 | 交付封包目录后缀 | **V4_2026-10-30** | 每次重新出包 |
| 构建指纹 | 受控配置与产物的 SHA-256 清单 | 见 `01_软件封包/交付产物_SHA256.txt`、`01_软件封包/app/config/SHA256SUMS` | 任一受控文件变动 |

> **历史目录处置**：`封包V3`、`封包V3_2026-10-29`、`封包V2/app/dist…dist8`、旧 `立项文件V1/V2/V3` 均为历史副本，**不再是有效交付物**，仅留作追溯。当前唯一有效交付包为 `LabBridgeV4/`。

### 处理原则（V4 沿用 V3 并补强）

| 动作 | 说明 |
|---|---|
| 去重 | 同一事实只在权威文档保留一份原文，其余以交叉引用指向，避免多处漂移 |
| 归并 | 数据分级、最小暴露面、日志、证据链统一收进 05 号文档 |
| 提纯 | 删除解释性长段落，只保留可落地规则、量化基线、结论 |
| 补强 | 补入版本溯源台账（12 号），集中承载分散在各文末的变更记录 |
| 校核 | **每条结论必须能被 `01_软件封包/app/code/` 源码或 `config/` 受控文件反向验证** |
| 保留 | 量化基线、红线、条款对应关系、不适用声明原文保留，不得改写数字 |

## 四、三条全局主线（每份文档都受其约束）

1. **方法论主线**：以 ISO 9001 过程方法、风险思维、PDCA 循环作为顶层框架；摒弃泡沫式 AI 项目，采用小项目试点、人在回路、资产沉淀、分阶段迭代。
2. **认知主线**：AI 是专业能力的放大杠杆，不是追热点的理由。两条能力路线——深度专精（行业合规、ISO 体系）与广度（Agent 编排、工作流设计）。
3. **输出主线**：对外只输出受控 AI 试点 POC + 合规证据包，单点小范围落地，不做无依据的全公司规模化推广。

## 五、五条项目红线（不可协商）

| # | 红线 | 落地钩子 |
|---|---|---|
| 1 | 敏感数据必须等风险控制措施部署评审完成后才可接入，**禁止提前加载** | `labbridge_gate.StageGate` |
| 2 | 无论何种模型处理敏感数据，坚持人在回路；高风险判定、最终结论**由人终审** | `labbridge_gate.ApprovalGate` |
| 3 | **全程留痕**：数据导入、模型调用、输出、人工修订须记录时间戳、操作员、版本 | `labbridge_auditlog.AuditLog`（哈希链） |
| 4 | Demo 敏感场景结论可作正式项目决策依据，但 **Demo 本身不等于生产级上线系统** | 证据包 DEMO 声明 |
| 5 | 试点验收后扩大范围**必须重新独立立项、新建 POC**，禁止原项目直接扩容 | 《立项边界》约束 |

> 红线 1–5 完整原文见 02 号文档第五节。
